# ECDSA signature verification

This package verifies an ECDSA signature using affine point arithmetic over
one small fixed prime-field curve. It exercises curve and public-key checks,
extended-Euclidean modular inversion, binary double-and-add, and the ECDSA
verification equation. The curve is deliberately tiny for deterministic
cross-language benchmarking; this package makes no security claim and is not
for cryptographic use.

## Contract

- ABI: `i64_array_bytes_output`; symbol: `ecdsa_signature_verification`.
- Input is exactly `[p,a,b,gx,gy,n,qx,qy,z,r,s]`.
- The domain tuple `[p,a,b,gx,gy,n]` must be exactly `[17,2,2,5,1,19]`, for
  `y^2 = x^3 + 2x + 2 (mod 17)`, base point `G=(5,1)`, and prime group order
  19. The finite curve has 18 affine points plus the point at infinity, so
  every non-infinity point is in the subgroup generated by `G`.
- The field count follows by enumerating the curve's right-hand side over
  `x=0..16`: it is a quadratic residue for exactly
  `x in {0,3,5,6,7,9,10,13,16}`, contributing two points each, plus infinity.
- The public key `Q=(qx,qy)` must use normalized coordinates in `0..16`, lie
  on the curve, and satisfy `[19]Q = infinity`. `z` is the 5-bit digest
  integer after ECDSA's `bits2int` conversion and must be in `0..31`; the
  verification equation reduces it modulo the group order. The
  signature scalars must satisfy `1<=r,s<=18`.
- After validation, compute `w=s^-1 mod 19`, `u1=z*w mod 19`,
  `u2=r*w mod 19`, and `R=u1*G+u2*Q`. The signature is valid exactly when
  `R` is not infinity and `R.x mod 19 = r`.
- A valid signature writes byte `1`; an invalid signature writes byte `0`;
  success returns `1`. Malformed input returns `-1`. Null output or capacity
  below one byte returns `-2`, with no output write. Maximum valid input is
  11 signed 64-bit words; the parser accepts up to 12 to reject a trailing
  value explicitly.
- Workspace is capped at 512 bytes. The fixed field and order keep every
  intermediate safely within signed 64-bit arithmetic.

## Complexity

Affine point addition uses a constant number of field operations. Extended
Euclid computes each modular inverse in `O(log n)` integer steps, and binary
double-and-add takes `O(log n)` point additions per scalar multiplication.
Validation and ECDSA verification therefore use `O(log n)` point operations
and `O(log n)` integer steps, with `O(1)` auxiliary space. In this benchmark,
`p=17` and `n=19` are fixed, so the bounded calls have a small fixed maximum.

## References and independent check

The verification method and digest conversion follow §6.4.2 of the
[NIST FIPS 186-5 PDF](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.186-5.pdf);
the domain-parameter validation context is in [NIST SP 800-186](https://csrc.nist.gov/pubs/sp/800/186/final). This
benchmark uses a separately selected toy curve rather than a recommended
cryptographic domain. Its point count and order are checked from the finite
field definition. No NIST text, source code, or official test vectors are
copied.

The primary reference follows ECDSA's modular-inverse and double-scalar
verification equation. The independent reference instead exhaustively
recovers the small public scalar and scans all possible nonces, checking the
signing relation directly. It uses repeated point addition and a brute-force
field inverse, so it does not duplicate the primary verification arithmetic.

## Workload and files

[`workload.json`](workload.json) covers two valid signatures, altered
signatures, invalid curve/domain/public-point/scalar inputs, malformed frame
lengths, null input, and short output capacity. The workload bytes are
little-endian-neutral because the output is one byte.

Package-local references and static helpers are
[`primary_oracle.py`](primary_oracle.py),
[`independent_oracle.py`](independent_oracle.py),
[`verify_workload.py`](verify_workload.py), and
[`check_inventory.py`](check_inventory.py). No project program, test,
checker, build, compiler, or benchmark has been run for this package.
