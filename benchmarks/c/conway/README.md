# Conway look-and-say step

The pinned Java `Conway.generateNextElement` uses `(?<=(.))(?!\\1)` to split an ASCII string. A split occurs before a character when its predecessor is not CR or LF and differs from it; Java regex `.` does not match those line terminators. The source emits each resulting segment as its decimal length followed by its first character, even when a segment contains multiple different characters. The benchmark preserves that behavior and returns the generated bytes without a terminator; the source's reusable `StringBuilder` has no observable effect on the result.

## Contract

- Uses the `i64_array_bytes_output` ABI. Input is `[text_length, ASCII_codepoint_0, ...]`.
- `text_length` must be 1 through 128, the array length must equal `text_length + 1`, and each codepoint must be in 0 through 127.
- The pinned Java regex splits between unequal adjacent characters when its preceding-character `.` match succeeds. Java `.` excludes carriage return and line feed, so no split occurs after either character; the source then emits each resulting segment’s length and first character, even if a segment contains differing characters. The ports preserve this behavior. The returned scalar is the exact number of output bytes; no NUL terminator is appended.
- Invalid shape or codepoints return `-1`; insufficient output capacity returns `-2`.
- A 128-character input produces at most 256 output bytes.

[`workload.json`](workload.json) covers the classic sequence examples, arbitrary ASCII symbols, control bytes, CR/LF regex edge cases, multi-digit run counts, maximum-size alternating input, and invalid inputs.

```sh
python3 benchmarks/build_abi.py --family i64_array_bytes_output --algorithm conway --language rust
python3 benchmarks/run_i64_array_bytes_output.py --build-manifest build/i64_array_bytes_output/c/conway/rust/build.json
```
